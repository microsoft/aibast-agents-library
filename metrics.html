Where these numbers come from

Downloads = git clones + jsDelivr CDN file hits + GitHub release asset downloads. A clone pulls the whole library; a CDN hit is a single file fetched by an installer, an agent, or a browser. GitHub only exposes a rolling 14-day traffic window, so scripts/build_metrics.py snapshots it into state/metrics_history.json, deduplicated by date — the all-time total grows from the first day of tracking and never double-counts.

What is not counted. The install one-liners fetch over raw.githubusercontent.com, which publishes no counter of any kind. Installs that take that path are invisible here, so treat every figure on this page as a floor, never a total. Installer fetches counts only the copies served through the CDN.

On clones. GitHub counts every actions/checkout as a clone, and this repository runs registry-build and preflight workflows on push. The estimated CI baseline is published as ci_clone_estimate alongside clones_excluding_ci_estimate in the snapshot. Agent file fetches is the narrowest and most trustworthy number on this page.

On unique counts. GitHub reports uniques per 14-day window, not per day, so daily unique figures cannot be summed into a true all-time unique. The headline unique cloners figure is GitHub's own 14-day number; the daily-unique sum beside it is an upper bound, since one machine cloning on three days counts three times. Clone counts and CDN hits have no such caveat — they are plain event counts and do accumulate exactly.

On traffic gaps. The GitHub traffic endpoints need a token with repository administration read access, which the Actions GITHUB_TOKEN cannot be granted. Without a METRICS_TOKEN secret the snapshot reuses the last authorized read rather than zeroing the figures, and the stamp above says so.
